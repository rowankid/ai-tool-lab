Agent / Obsidian / Content Ops

AI 内容工作流里的单一事实源怎么建：别让 Agent 在 5 份上下文里来回猜

披露：本文不包含必须点击的商业链接。目标不是鼓励你再加一个“知识管理系统”，而是把内容事实、执行边界、 发布资产和自动化摘要分开，减少 Agent 返工、误改和重复贴上下文。

一句话结论

如果你已经在用 Claude Code、Codex、Obsidian 或定时自动化做内容，真正该先补的通常不是新提示词，而是 单一事实源：把事实与来源放在一处，把执行边界放在一处，把公开资产放在站点仓库里， 再让自动化只负责整理、补链、校验和汇总。否则 Agent 每次都会在聊天记录、零散 Markdown、旧页面和临时想法之间来回猜。

为什么这题现在值得单独写

2026 年公开讨论里，一个很明显的信号是：大家已经不满足于“让 Agent 帮我写一段”，而是在讨论如何把 Obsidian、Claude Code、Codex 和定时任务接成长期系统。问题也随之变化成： 同一条事实到底放哪？下次自动化回来该信哪份版本？手机审批时又该看什么摘要？

  • X 的公开痛点在变：有人把 Claude Code + Obsidian 当成第二大脑，也有人强调 Codex 真正的 unlock 是“给更高层目标和上下文”，不是不断给碎命令。
  • 官方能力已经支持长期工作流：Anthropic 和 OpenAI 都把 recurring tasks、session history、instructions、skills、remote/mobile 接力写进公开文档。
  • 中文内容站最容易在这里返工：同一事实散落在笔记、灵感库、HTML、自动化线程和手动复盘里，最后谁都不确定哪份才是最新版本。

先看 4 个事实锚点

  1. Anthropic 已把持久指令和记忆写成正式能力： `CLAUDE.md` 会在会话开始时读取，auto memory 会跨会话保存 learnings，Claude Code 也支持 schedule recurring tasks。
  2. OpenAI 已把“回到同一线程继续推进”定义成自动化场景： 2026-04-23 的 OpenAI Academy `Automations` 页面明确写到，部分 automations 可以回到同一 conversation，沿用已有上下文继续做事。
  3. 手机接力不是替代事实源，而是减少返工： OpenAI 在 2026-05-14 的 `Work with Codex from anywhere` 说明里强调，quick check-in 能防止 unnecessary rework，但前提是线程里已经有足够清楚的上下文和审阅节点。
  4. Google 仍要求独特、有价值、页面体验清楚： 2025-05-21 的 Search Central Blog 继续强调 AI 搜索里仍该优先做 unique, valuable content 和 good page experience，这意味着“事实源混乱”最终会伤害公开页面质量。

单一事实源不等于“所有东西放一个文件”

很多人把 single source of truth 理解成“找一个超大文档，全都塞进去”。这会让 Agent 更难用，因为事实、策略、操作边界、草稿和发布资产混在一起。 对内容站更稳的做法是：一个系统里只有一份主记录，但不同类型的信息分层存放。

事实层

放可核验来源、日期、结论、冲突和待确认项。适合存在 Obsidian / wiki 页面，而不是散在聊天记录里。

执行边界层

放 AGENTS.md、CLAUDE.md、automation prompt、允许修改范围和禁止动作。这里回答的是“能做什么、不能做什么”。

发布资产层

放最终 HTML、首页入口、Hub、sitemap 和披露文案。这里是公开版本，不再承担原始研究记录。

复盘摘要层

放每小时看板、数据表、自动化记忆。它们是索引和状态，不应该反过来成为正文事实源。

一条适合中文内容站的最小结构

  1. 原始事实只进知识库：官方链接、X 公开讨论、日期、问题定义、风险判断，统一写进 wiki 页面或灵感库。
  2. 执行规则只进 agent 指令：例如允许改哪些目录、哪些动作必须人工确认、哪些平台只能观察不能登录互动。
  3. 公开页面只放整理后的结论：首段给结论，正文给读者可执行框架，来源放在文末，避免把研究笔记原样贴进 HTML。
  4. 自动化只写回两个地方：灵感库/看板和站点文件。不要让它额外生成一份平行“主记录”。
  5. 每次迭代都标日期：尤其是 Claude Code / Codex / Google 这类变化快的主题，写清核验日期，避免下轮自动化拿旧说法继续扩写。

滚动上下文文件怎么维护，才不会把主记录越写越乱

这轮公开讨论里，一个很有代表性的用法是：把定时任务用来 持续更新一份 Markdown 上下文文件，让 Agent 在上下文窗口之外也能接上长期工作流。这个方向值得借，但要先分清 什么能定时写回，什么不能。

  • 适合定时写回的内容：本轮新增来源、已完成动作、验证结果、阻塞项、下次要看的页面或文件。
  • 不适合定时写回主记录的内容：未经核验的事实结论、会影响公开表述的判断、对外发布时间、商业关系变化。
  • 更稳的分工：让 scheduled tasks 或 automations 只更新“复盘摘要层”，再由你把确认后的结论写回知识库主记录和 HTML 页面。

对内容站来说，最容易失控的不是“没有上下文文件”，而是把上下文文件误当成事实源本身。更稳的做法是： 上下文文件负责续航，主记录负责定版。

Memory 不是主记录：它更像召回层，不是公开结论层

随着 Claude 和 Codex 都越来越强调 memory、persistent thread 和 mobile check-in，最容易出现的新误区是：既然工具更会“记住”，是不是就能少维护主记录。更稳的答案是否定的。 memory 更适合减少重复解释、续上工作语境；它不该替代你对事实、披露、发布日期和公开表述的定版。

  • Anthropic 在 2026-03-02 把 memory 扩到所有 Claude 用户：这说明“跨会话记住上下文”正在变成默认能力，但它记住的是相关上下文，不是你已经核定的公开版本。
  • Anthropic 在 2026-02-25 公布 scheduled tasks：更适合定时整理摘要、列阻塞项、回顾变化，而不是替你改写事实主记录。
  • OpenAI 在 2026-05-14 公开手机接力：官方强调的是 quick check-in、change direction 和 prepare a concise briefing，本质上仍是帮助你更快判断，不是免掉主记录维护。

如果你把 memory 直接当真相源，最常见的后果就是：X 上的问题线索、上轮 automation 的临时判断、旧版 FAQ 和新版 HTML 一起混进“长期记忆”，下轮又被当成事实继续扩写。

适合 / 不适合这样做的人

更适合
  • 已经有 Obsidian、Markdown 知识库或固定站点仓库的人。
  • 已经开始跑 Agent/automation，正在被“重复贴上下文”和“版本打架”拖慢的人。
  • 想把内容做成长期资产，而不是只求一两次爆文的人。
不太适合
  • 你现在连题库、页面结构和发布边界都还没有，先别急着做复杂分层。
  • 你只想全自动堆量，不准备人工核事实、核披露、核外部动作。
  • 你的团队仍然把聊天记录当最终决定，却不愿维护公开可追溯的项目页。

最容易翻车的 5 个点

  • 把灵感库当正文仓库：灵感库只该记录候选题、痛点和来源，不该承载成稿事实。
  • 把 AGENTS.md 写成项目百科：边界文件只写长期规则和入口索引，细节回到独立 Markdown 页。
  • 让自动化生成第二份“总结真相”：日报和 memory 应该摘要本轮动作，不应变成另一套事实数据库。
  • 页面改了，知识库没改：下轮自动化又会按旧结论继续扩写，造成“站点和 wiki 互相打架”。
  • 把外部讨论当硬规则：X 适合找问题线索，不适合当产品行为和搜索规则的最终依据。

这套结构怎么反过来提升 SEO/GEO

单一事实源的价值不只在“Agent 少返工”，还在于它能让公开页面更稳定地满足搜索意图。因为你会被迫区分： 哪些是事实、哪些是推断、哪些是中文用户边界、哪些只是临时观察。这样写出来的页面更容易做到：

  • 首段直接回答问题，而不是先讲工具背景。
  • 至少 3 个事实点能回到官方来源核对。
  • 站内内链更清楚：方法页、QA 页、Hub 页、关系层页各自承担不同角色。
  • 更新时能优先补旧页，而不是每次都新开一篇相似薄内容。

FAQ

自动化应该定时写回哪一类文件？

优先写回灵感库、运营看板、每日数据表、automation memory 这类 摘要层文件。这些文件适合记录本轮观察、验证、风险和下一步。主记录型 wiki 页面与公开 HTML 页面，更适合在你确认后再更新。

如果同一条事实在知识库、HTML 和简报里不一致，先改哪份？

先改知识库里的事实主记录，再同步公开 HTML，最后让简报摘要引用新版本。否则下轮自动化会继续从旧主记录里扩写，造成“公开页已变、内部判断还停在旧版本”的返工。

需要额外维护一份“超大上下文文件”吗？

通常不需要。更好的做法是保留分层结构：知识库记事实，`AGENTS.md` 或 `CLAUDE.md` 记边界，公开站点记对外版本，日报和看板记本轮摘要。只有当你确实需要 跨多轮续跑同一任务 时，才额外维护一份滚动上下文文件，而且它不该替代主记录。

Memory、滚动上下文文件和知识库主记录，应该先信谁？

优先级应该是知识库事实主记录 > 已核定公开 HTML > 滚动上下文文件 / automation memory。前两者负责“什么是真的、什么已经对外发布”，后两者负责“这轮发生了什么、下轮从哪接着做”。
