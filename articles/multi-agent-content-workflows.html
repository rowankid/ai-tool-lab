Agent Workflow / Parallel Work

多 Agent 协作什么时候有用，什么时候浪费：Claude Code / Codex 内容站工作流边界

披露：本文不包含 Claude Code、Codex 或其他 agent 工具的联盟链接。目的不是鼓励你“多开越多越好”，而是把多 agent 的适用边界、验证方法和中文内容站场景写清楚。

一句话结论

对内容站来说，多 agent 只在任务彼此独立、输出容易汇总、主会话不该被大量日志和检索结果淹没时有用。 如果任务需要反复改同一篇文章、频繁来回确认或共享大量上下文，单主会话通常更稳。

先看 5 个事实：为什么 2026 年 5 月还要重写这篇

  • X 上的公开讨论已经从“会不会用 agent”转到“怎么并行跑”：例如 Theo 关于“为什么要开多个 Codex 窗口”的公开提问 与 Yann 把多会话、Plan Mode、subagent、safe permissions setup 打包成工作流卖点的公开帖， 说明用户痛点已从单次提示词转到并行协作与边界设计。
  • Anthropic 官方把 subagent 定义成“上下文隔离器”：官方文档明确说，Claude 遇到匹配描述的任务时，会把它委派给 subagent，让它在独立窗口里工作后返回结果；这更接近“隔离研究噪音”，不是“多开越多越强”。
  • OpenAI 在 2026-05-14 把“远程接力”正式做成产品能力：Codex 现在可以在手机上审阅输出、批准命令、看 diff 和测试结果。并行因此更常见，但也更要求你提前写清谁负责判断、谁只负责执行。
  • OpenAI 在 2026-05-08 进一步把安全边界讲具体了：官方把 agent 治理拆成 sandbox、approval policy、network policy 和 agent-native telemetry，等于告诉你并行不是只追求吞吐，而是先划清技术边界与审计边界。
  • GitHub 在 2026-02-13 也给了同一方向的信号：Agentic Workflows 允许用 Markdown 描述自动化目标，而且工作流默认只读、写操作走预批准的安全输出。行业信号已经很一致了: 真正成熟的并行体系，先约束，再放权。

中文内容站里，哪些任务适合拆成多 agent

适合并行
  • 一个 agent 查官方来源并补事实核查，另一个只做首页、Hub、`sitemap.xml` 和链接入口同步。
  • 一个 agent 扫站内死链与相对路径错误，另一个只核对披露、`rel="sponsored"` 和 CTA 边界。
  • 一个 agent 跑 HTML 解析/站内链接检查，另一个整理灵感库、题库与运营看板状态。
  • 针对彼此独立的 2 个主题簇做只读研究，例如一个查 Claude Code 官方文档，一个查 Codex 官方文档，最后主会话汇总。
不适合并行
  • 5 个 agent 同时改同一篇文章的结构、标题、结论与 CTA，最后只会带来合并成本。
  • 需要你边看边改方向的任务，例如“这篇文章的论点还不够稳，先跟我讨论再写”。
  • 需要共享大量上下文的链路，例如“从题库判断、到文章框架、到改首页入口”全都强耦合在一起。
  • 任何带登录态、验证码、付款、KYC、删除或外部发布的动作。

一个最实用的判断标准：这件事会不会污染主会话上下文？

如果某个子任务会生成一大堆你最终并不想反复引用的内容，比如检索结果、测试日志、HTML 检查输出、几十个文件路径，那么它很适合交给 subagent 或独立 worktree 会话。Anthropic 文档把这类场景直接列为 subagent 的核心用途。

但如果子任务的产出本身就是你下一步必须逐句推敲的正文、框架和商业边界，那就别急着并行。此时上下文不是负担，而是你判断质量的基础。

Claude Code / Codex 各自给了什么官方信号

  • Claude Code：官方 tutorials 把 `claude --worktree feature-auth`、`claude --permission-mode plan` 和 “use a subagent to investigate ...” 明确写进常见工作流；subagents 文档还给了 `background`、`permissionMode`、`isolation: worktree` 这些配置位。
  • Codex：OpenAI 在 2026 年 2 月 2 日发布的 Codex app 介绍里，直接把 “multiple agents in parallel” 和 “built-in support for worktrees” 作为产品核心；Codex CLI 官方页则把 subagents 和 approval modes 一起列为正式能力，不是隐藏开关。

这两个官方信号都指向同一件事：并行是为了隔离风险与上下文，不是为了把所有任务一股脑拆碎。

内容站里的 3 个推荐并行模式

  1. 研究与发布拆开：主会话负责定标题、结论和风险边界；子 agent 只查来源、提炼事实点和整理链接。
  2. 写作与站点同步拆开：主会话产出正文；另一个 agent 只负责把新页接到首页、学习页、Hub、`sitemap.xml` 和 QA 流程。
  3. 验证单独拆出：把 HTML 解析、站内链接检查、`curl` 校验、`rsync` 预发布快照交给独立 agent，避免验证日志挤满主对话。

发布前先过一遍这个 6 问检查表

  1. 任务是否彼此独立？ 如果两个 agent 最终都要反复改同一篇正文，就别并行。
  2. 主会话会不会被日志淹没？ 如果会，研究、测试、抓链接更适合拆给子 agent。
  3. 结果是否容易汇总？ 最好能回传成 3 到 7 条结论，而不是一长串原始输出。
  4. 是否涉及登录、支付、验证码或外部发布？ 涉及这些动作就不要交给并行 agent 自动推进。
  5. 写清谁能改文件、谁只能读吗？ 没写清 ownership，最后大概率是合并冲突和重复劳动。
  6. 有没有验证闭环？ 至少要约定 HTML 解析、站内链接检查、入口同步和 `curl` 标题校验由谁负责。

最常见的 4 个误区

  • 误区 1：任务一复杂就该多开。实际上，高耦合任务更需要单线程判断。
  • 误区 2：多 agent 一定更快。很多时候你只是把串行思考换成了并行返工。
  • 误区 3：subagent 越多越专业。Anthropic 官方也提醒，返回结果过多仍会消耗主会话上下文。
  • 误区 4：用了 worktree 就等于安全。worktree 只隔离文件改动，不替你决定哪些动作必须人工确认。

FAQ：3 个最容易问错的问题

  • 多 agent 会不会天然更快？ 不会。只有在子任务独立、回传可摘要时才会更快；高耦合写作任务往往更慢。
  • 手机能审批了，是不是就能远程发布？ 不是。远程审批解决的是接力，不是合规替代；发布、收款、KYC、外部发帖仍要人工确认。
  • GitHub/Claude/Codex 都在讲 agent，是不是应该马上全盘并行？ 也不是。官方共同强调的是受控环境、默认边界和可审计，而不是无上限拆任务。

适合谁 / 不适合谁

  • 适合：已经有基础内容 SOP，知道什么叫完成、什么叫不该发布，只是想把研究、同步和验证并行化的内容团队或一人公司。
  • 不适合：还没有题库、内链规则、披露边界和验证清单，却想靠“多开 agent” 直接提高产量的人。

如果你只拿走一条执行建议

先把多 agent 用在研究、同步、验证这三类副任务上，不要先把它用在“共同写一篇文章”。对中文内容站来说，最稳定的模式通常是： 主会话定结论，子会话查事实，独立会话做站点同步和验证。
