OpenSpec / Superpowers / Codex / Content Ops

OpenSpec + Superpowers + Codex 的内容生产闭环：别再把 Agent 工作流拆成 5 段

披露：本文不包含必须点击的商业链接。目标不是把一套开发者工作流包装成内容玄学，而是解释为什么中文内容团队一旦开始用 Agent， 最缺的往往不是“再多一个命令”，而是一条从规格、执行到验证都能复用的闭环。

一句话结论

如果你已经在用 Agent 做选题、改稿、补站点和写周报，真正缺的通常不是更多 prompt，而是把 OpenSpec、Superpowers 和 Codex 放回同一条闭环： OpenSpec 管“这轮到底要变什么”， Superpowers 管“Agent 该按什么纪律推进”， Codex 管“实际改文件、跑验证、交结果”。 这样才能避免内容工作流反复停在“想到一个方向”“跑了一轮自动化”“结果又回头补边界”的碎片循环里。

为什么这题现在值得补上

最近几轮公开讨论和官方更新都在往同一个方向收敛： Agent 不再只做单次命令，而是在接手更长的工作流。问题也从“它能不能写”变成“它到底该按什么规格执行、谁来约束质量、哪里停下来让人拍板”。 对中文内容团队来说，这正好对应 3 个现实痛点：

  • 方向漂移：每小时都在补页面，但没有一份清楚的行为变更定义。
  • 执行散乱：有时先写草稿，有时先补内链，有时先跑 QA，顺序不稳定。
  • 验证缺席：页面改了，但入口、sitemap、事实核查和风险边界没有一起跟上。

先看 5 个事实锚点

  1. OpenSpec 的官方定位就是 spec-driven development： Fission-AI 的官方仓库把它定义成面向 AI coding assistants 的 spec-driven development 框架，重点是 proposal、design、tasks 和 spec delta，而不是让需求只存在聊天记录里。
  2. Superpowers 的官方定位不是“技能包”，而是完整方法论： obra 的官方仓库直接把它写成“an agentic skills framework and software development methodology”，也就是它强调的不只是工具，而是 brainstorming、计划、验证、review 这些执行纪律。
  3. OpenAI 已经把 recurring work 讲成 Codex 的正式场景： 2026-04-23 的 OpenAI Academy `Automations` 页面明确把 recurring tasks、同线程续跑和可审阅结果写成公开能力。
  4. OpenAI 也把“简报与决策包”讲成内容团队能借用的模板： 2026-05-15 的 `How business operations teams use Codex` 里，把 scattered context 收束成 decision-ready briefs、updates 和 packets。
  5. 手机接力和远程推进会放大流程差异： 2026-05-14 的 `Work with Codex from anywhere` 说明，线程会跨设备继续推进；这反而更要求你把规格、执行纪律和验证节点提前写清楚。

这三层各自负责什么

OpenSpec：规格事实层

回答“这轮到底改什么、为什么改、什么不改、什么算验收通过”。适合承接 proposal、design、tasks 和非目标。

Superpowers：执行纪律层

回答“Agent 应该先澄清、先计划、先验证还是先并行”，避免每次都凭感觉切流程。

Codex：落地执行层

回答“具体改哪些文件、跑哪些检查、输出哪些结果、哪些动作必须停下来给人看”。

知识库 / 站点：沉淀层

知识库留主记录，公开站点留对外版本；不让一次聊天记录反过来变成长期事实源。

把它翻译成中文内容团队能执行的闭环

  1. OpenSpec 先定变化：例如“这轮要补的是 open rate 诊断顺序，而不是新写一篇泛 newsletter 工具页”。
  2. Superpowers 再定推进方法：先读现状、再判断补旧页还是新开页、再决定验证顺序，而不是一上来就扩写。
  3. Codex 最后执行：改 HTML、补内链、更新入口、更新 sitemap、跑 HTML 解析和站内链接检查。
  4. 看板与数据表只记录这轮变化：不重新发明第二套事实源。

如果你已经读过 单一事实源、 运营简报、 automations 边界 和 内容 QA， 这篇就是把它们串回同一条完整路径。

最容易误解的 4 个点

  • 误解 1：OpenSpec 只适合工程需求。其实内容系统里一样有“行为变化”“非目标”“验收标准”。
  • 误解 2：Superpowers 只是让 Agent 更啰嗦。真正价值在于固定顺序和验证纪律，减少返工。
  • 误解 3：Codex 负责所有判断。更稳的分工是它负责执行与汇总，最终取舍仍由人拍板。
  • 误解 4：闭环等于多写文档。不是。闭环的目标是减少重复解释、重复返工和重复补洞。

一条适合内容站的最小执行顺序

阶段 要回答的问题 对应工具层
规格 这轮要改什么，不改什么，验收标准是什么 OpenSpec
计划 先补旧页还是先开新页，要不要并行，哪些文件会受影响 Superpowers
执行 具体改哪些 HTML / Markdown / sitemap / 入口页 Codex
验证 HTML 能否解析，站内链接是否正常，标题和入口是否命中 Codex + Superpowers
沉淀 这轮变化、风险和下一步写回哪里 知识库 / 看板 / 数据表

适合谁 / 不适合谁

更适合
  • 已经有知识库、站点和自动化，但总在“页面补了一半又换方向”的团队。
  • 想把 Agent 用在长期内容资产，而不是一次性聊天出稿的人。
  • 愿意把外部发布、支付、KYC、登录等高风险动作保留人工边界的人。
不太适合
  • 还没有基本题库、看板和站点入口，先别把流程叠太重。
  • 只想批量堆页，不准备做事实核查和验证的人。
  • 希望 Agent 直接代替你做最终商业决策或对外发布的人。

如果你今天只落一个模板

把每一轮内容迭代都压成下面 5 格，比继续补碎 prompt 更有用：

  1. 本轮变化：到底要补哪一页、哪一种缺口。
  2. 非目标：这轮明确不碰哪些相似页和外部动作。
  3. 执行顺序：读现状、改文件、补入口、跑检查、写回看板。
  4. 验证证据：HTML 解析、链接检查、`curl` 标题命中、`sitemap.xml` `lastmod`。
  5. 人工检查点：是否值得发布、是否要继续扩题、是否涉及外部动作。
