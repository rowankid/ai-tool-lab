Newsletter · Automation

beehiiv、Kit、Substack 自动化怎么选：欢迎序列、分支能力与中文创作者边界

披露：本文会提到 beehiiv，并在相关位置保留 partner link；如果你通过这些链接注册或付费，我可能获得佣金， 这不会增加你的费用。Kit、Substack 本文只放官方普通链接。本文不建议买名单、导入未授权邮箱、伪造互动或把自动化当垃圾邮件放大器。

一句话结论

如果你现在最需要的是多步欢迎序列、条件分支、重入控制和后续 nurture，优先看 beehiiv 或 Kit； 如果你更看重轻量发布、社区发现和低复杂度，Substack 仍然更省心。对中文创作者更实用的判断不是 “哪个功能最多”，而是你有没有足够稳定的内容资产，值得你去维护自动化。

更直接地说：beehiiv 更像媒体增长栈，Kit 更像创作者漏斗栈，Substack 更像作者发布栈。 如果你还没把订阅承诺、欢迎邮件和 3 篇核心内链写清楚，先别急着研究复杂自动化，先补 欢迎邮件 5 封序列、 Lead magnet 设计 和 投递底线。

为什么这个选题现在值得做

这轮在 X 的公开讨论里，围绕 newsletter 的痛点已经不只是“要不要做”，而是“该不该把 AI 和自动化接到欢迎链路、分发和名单质量上”。 我看到的高频抱怨有三类：一类是每次都要手动拼欢迎邮件；一类是平台功能不少，但不知道该不该一开始就上自动化；还有一类是担心自动化做重了， 反而把名单质量和投递声誉搞坏。

  • 公开讨论 1：把 AI 当成“Substack employee”，试图减少每天重复的内容分发劳动。
  • 公开讨论 2：用自动化收集 newsletter 研究队列和 X 话题线索，但不知道该落在哪个邮件平台。
  • 判断：这些讨论能提供痛点，但不能代替规则来源；平台能力仍以官方帮助中心和价格/计划说明为准。

先抓 4 个事实核查点

  1. beehiiv 把单封欢迎邮件和多步 welcome automation 明确分开：单封 welcome email 所有计划可用； multi-step automation 走 paid plans，而且如果你同时开了欢迎邮件和 Signed Up 自动化，新订阅读者会收到两次欢迎消息。
  2. beehiiv 的自动化不是“邮件定时器”这么简单：官方帮助中心明确提供 trigger、action、delay、branch、 re-entry 等构件，并且提醒修改 live automation 前要先确认没有订阅读者正卡在目标步骤里，否则可能把人卡住。
  3. Kit 的欢迎自动化是“Sequence + Visual Automation”两段式：官方文档明确要求先写 Sequence，再用 Visual Automation 把 Form/Landing Page 接进去；Newsletter Plan 只有 1 个 basic Visual Automation 和 1 个 Sequence。
  4. Substack 公开文档强调的是 welcome email 和 recommendations，而不是可视化分支自动化：我查到的官方帮助中心重点是 4 类 welcome email、 welcome page 与 recommendations；没有找到与 beehiiv / Kit 同等级的分支式 automation builder 文档。这个结论是基于当前公开文档的推断，不排除未来变化。

三平台差异，先看这张表

平台 更像什么 欢迎链路 自动化深度 更适合谁
beehiiv 媒体化 newsletter 增长栈 单封 welcome email 或多步 welcome automation 有 trigger、delay、branch、re-entry、template 已经有内容站，想把订阅、调查、升级、再激活串成系统的人

beehiiv：什么时候值得上欢迎自动化，而不是只发一封 welcome email

如果你已经有 3-5 篇站内核心文章、愿意做 survey / source-based onboarding / re-engagement，beehiiv 的优势会很明显。 它不是只能发 3 封欢迎邮件，而是能把“谁从哪里来、接下来该看什么、满足什么条件后升级或分流”做成一张流程图。

  • 优点：官方文档明确支持多种 trigger、condition、branch 和 re-entry；适合把 栏目设计、 打开率诊断 和 推荐增长 串起来。
  • 代价：你需要先把站内资产和名单质量规则写清楚，否则自动化只会放大混乱。
  • 中文用户边界：如果你还在摸索主题、域名认证和收款/KYC，先用单封 welcome email 或简化 flow 更稳。

如果你已经确定要走“内容站 + owned audience”路线，可以先看 beehiiv 官方站， 但别在没写清欢迎序列和名单质量之前就急着开复杂分支。

Kit：更像“把订阅表单接进 nurture 漏斗”的平台

Kit 的官方文档把欢迎序列拆得很直白：先建 Sequence，再用 Visual Automation 把 Form 或 Landing Page 接入。 这意味着它天然更适合“订阅后进入一段 nurture 流程，再按标签或行为继续分流”的场景。

  • 优点：Visual Automations 的 entry point、tag、sequence 组合清晰，适合做表单到 nurture 的创作者漏斗。
  • 限制：Newsletter Plan 只有 1 个 basic Visual Automation 和 1 个 Sequence；如果你要多条流程，很快会碰到计划边界。
  • 中文用户边界：如果你当前主线不是课程、咨询、产品漏斗，而是先把内容写厚，Kit 的复杂度未必值得你立刻承担。

一个实用判断是：如果你最关心的是“如何把不同入口订阅者打标签、进入不同 nurture 轨道”，Kit 比 Substack 更对路； 但如果你只是想先建立稳定更新，不一定比 beehiiv 或 Substack 更适合冷启动。

Substack：自动化更轻，但社区分发链路更自然

Substack 这轮最值得注意的，不是“它自动化弱”，而是它把 welcome page、welcome email、recommendations 和 subscribe flow 接得更自然。 如果你现在最缺的是“先稳定写，再借社区发现”，Substack 的轻量是优点，不是缺点。

  • 优点：welcome email、welcome page、recommendations 都比较直观，读者在订阅后还能继续看到你推荐的 publication。
  • 限制：从当前公开帮助中心来看，更像轻量 onboarding 和增长网络，不像 beehiiv / Kit 那样强调分支、延迟和后续 flow 控制。
  • 中文用户边界：如果你计划把 newsletter 深度接回自有站内内容系统、FAQ、lead magnet 和分层 nurture，Substack 的“够用”可能很快变成上限。

适合谁 / 不适合谁

更适合 beehiiv / Kit 的情况
  • 你已经有稳定更新节奏，且愿意维护 3-5 封欢迎序列。
  • 你需要按来源、标签、调查结果或订阅层级做分流。
  • 你想把 newsletter 接回站内文章、Lead magnet、升级或再激活流程。
更适合先用 Substack 的情况
  • 你主要目标是先稳定发起来，而不是一开始就搭复杂漏斗。
  • 你更需要社区发现和推荐，而不是多条自动化。
  • 你还没有足够内容库存，暂时不值得维护复杂 workflow。
三者都不该现在上的情况
  • 你还没写清楚订阅承诺，只想“先把表单挂上”。
  • 你打算导入未授权邮箱、买名单或靠 AI 批量群发。
  • 你还没把 SPF、DKIM、DMARC、退订和投诉边界搞清楚。

如果你现在就要做，建议顺序不是“先选平台”，而是这 5 步

  1. 先定义订阅承诺：读者留下邮箱后 7 天内会得到什么。
  2. 先写 3 封最小欢迎链路：兑现承诺、给阅读地图、解释下一步。
  3. 先把站内回访路径补齐：至少准备 3 篇高价值内链，例如 第二增长曲线、Lead magnet、欢迎序列。
  4. 再选平台：要分支和系统化，选 beehiiv 或 Kit；要低复杂度与社区分发，选 Substack。
  5. 最后才开复杂自动化：先验证订阅质量、打开/点击和退订，再逐步加分支。

中文创作者最容易忽略的 4 个边界

  • 别把自动化当内容替代：自动化只能放大你已有的价值交换，不能替代内容本身。
  • 别把欢迎序列写成连发促销：Google 的 sender guidelines 仍然强调认证、订阅同意和清晰退订。
  • 别把平台功能当战略：平台只是承载，真正决定留存的是主题、栏目和回访理由。
  • 别忽略迁移成本：如果你预计以后要把 newsletter 深度接回站内 SEO/GEO 资产，过轻的平台后面可能反而要重迁移。
